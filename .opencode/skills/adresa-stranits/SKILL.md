# Технический аудит сайта (методология «Текарт»)

Проводим технический SEO аудит сайта и оформляем результаты в `.docx` по заданному шаблону.

## Формат итогового документа

На выходе всегда `.docx` файл, оформленный по шаблону как в примере («Технический аудит Frontside.ru.docx»):
- Обложка: название аудита (24pt, #333333), дата (9pt, #942972), таблица данных проекта (Заказчик / Документ). Без брендинга «Текарт» — без копирайта, дисклеймера и контактов менеджера.
- «Содержание» — список разделов
- Основные разделы (Heading 1), подразделы (Heading 2), вложенные (Heading 3)
- Каждый подраздел: констатация фактов → недостатки с примерами и ссылками → блок «Рекомендация:» жирным
- Где нужно — код (robots.txt, JSON-LD микроразметка), таблицы, гиперссылки, изображения

## Язык и стиль

- Понятным русским языком, без воды.
- Рекомендации — четкие и по пунктам (формат «Проблема X. ... → Рекомендация: ...»).
- Придерживаться нейтрального, экспертного делового тона, как в образце.

## Шаг 0. Единый сбор данных (общий коллектор)

Перед анализом запусти общий краулер-коллектор — один обход собирает данные для всех модельных пунктов и кэширует результат:

```bash
python3 .opencode/tools/seo_collect/site_collect.py --url <URL сайта>
```

Скрипт печатает путь к JSON (строка `OUT=...`, по умолчанию `/tmp/opencode/seo_collect/<хост>.json`) и кэширует его на 2 часа. Дальше данные бери из JSON скриптом на Python — сайт повторно вручную НЕ обходи.

Что в JSON:
- `pages[]` — по каждой странице: `status`, `final_url`, `redirect_chain`, `title`, `description`, `meta_robots`, `canonical`, `lang`, `headings` (H1–H6), `h1`, `text`, `text_len`, `og`, `twitter`, `jsonld_types`, `jsonld_blocks`, `microdata_types`, `structured_types`, `links_internal` (абсолютные URL), `links_external`, `images`, `soft404`;
- `internal_link_status` — отклик каждой внутренней ссылки (`status`, `location`);
- `sitemap` (`found`, `urls`, `files`), `robots` (`status`, `text`), `external_links`, `stats`.

Ключи: `--refresh` — пересобрать кэш; `--limit N` — ограничить число страниц; `--no-link-check` — без проверки откликов ссылок (быстрее).

## Порядок работы по пункту 1.1 «Адреса страниц»

Действовать строго по шагам:

1. Заходим на сайт, указанный пользователем.
2. Формируем список URL:
   - Через `sitemap.xml`, если файл есть и рабочий.
   - Если файла нет/с ошибками/неполный — обходим сайт по меню, внутренней перелинковке и т.д.
3. Проверяем URL с точки зрения адресации:
   - **ЧПУ** — URL должен отражать суть страницы, формироваться транслитерацией, иметь дефис-разделитель, единый стиль форматирования, логичную структуру.
   - **Технические URL** — не должно быть `php`, `index`, сессионных и т.п. расширений.
   - **Множественные слеши** — страницы с `////` не должны отдавать 200.
   - **www / без www** — должен быть настроен 301 редирект на нужную страницу (canonical домен).
   - Любые другие найденные проблемы в системе адресации — описать.
4. Оформляем находки строго в формате «проблема → рекомендация».

### Что НЕ относится к пункту 1.1 (исключить из этого пункта)
Переносится в другие разделы аудита и не попадает в 1.1:
- Проблемы `sitemap.xml` (протоколы, битые ссылки, устаревшие даты lastmod, смешанный www, changefreq/priority) — это пункт про индексацию/sitemap (1.4.X).
- Отклики сервера (404, 301/302 редиректы на поддомены, битые ссылки) — это пункт про заголовки откликов / сервер (1.3, 4.x).

### Что можно включать как часть адресации
- Отсутствие ЧПУ (query-string вида `?page=...`).
- Нечитаемые/бессмысленные имена URL (`dele-m`, `services-port_tmrk_services`).
- Технические фрагменты в URL (`index`, `unfined` в адресе новости) — как аспект структуры адреса.
- Технический URL главной (`index.htm`).
- Отсутствие единообразия завершающего слеша.
- Положительные моменты тоже отмечать (например, корректный www/non-www редирект).

## Техника генерации .docx

Использовать Python библиотеку `python-docx` (уже установлена с флагом `--break-system-packages`):
```bash
pip3 install --break-system-packages python-docx
```

Рекомендуемая структура скрипта генерации (`/tmp/opencode/generate_audit.py`):
- `from docx import Document`, `from docx.shared import Pt, RGBColor`, `from docx.enum.text import WD_ALIGN_PARAGRAPH`
- `doc.styles['Normal'].font.size = Pt(10)`
- Обложка: заголовок (Pt(24), RGBColor 0x333333), дата (Pt(9), RGBColor 0x942972), таблица данных проекта (3 строки: шапка, «Заказчик», «Документ»), стиль `Table Grid`. Копирайт/дисклеймер/контакты «Текарт» не добавлять.
- Таблица данных проекта: `doc.add_table(...)`, стиль `Table Grid`
- Заголовки: `doc.add_heading('...', level=1/2/3)`
- Жирная «Рекомендация: » — `run.bold = True`
- Маркированные списки — стиль `List Bullet`

После генерации проверить содержимое документа чтением через `python-docx` и вывести итоговую структуру проблем/рекомендаций пользователю.

## Если проблем нет

Даже если по пункту проблем не выявлено — всё равно дай краткую подводку (зачем этот пункт нужен), а в блоке проблем напиши: «Проблем на сайте не обнаружено, исправления не требуются.»

## ОБЯЗАТЕЛЬНЫЕ ПРАВКИ ДМИТРИЯ (обязательно)
- Canonical: НИКОГДА не писать «поставить rel=canonical на все страницы сам на себя».
- Разбирать canonical только точечно и на примерах (пагинация; каталог с вариантами/цветами).
- Если по canonical нет полезного вывода — не писать про него вообще.
- Не описывать то, что не является проблемой.
