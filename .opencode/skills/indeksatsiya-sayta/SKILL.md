# Технический аудит сайта (методология «Текарт»)

Проводим технический SEO аудит сайта и оформляем результаты в `.docx` по заданному шаблону.

## Формат итогового документа

- Обложка: название аудита (24pt, #333333), дата (9pt, #942972), таблица данных проекта (Заказчик / Документ). Без брендинга «Текарт» — без копирайта, дисклеймера и контактов менеджера.
- «Содержание» — список разделов.
- Заголовки: Heading 1 / Heading 2 (1.4) / Heading 3 (1.4.1, 1.4.2, 1.4.3).
- Каждый подпункт: краткая подводка (зачем это нужно с точки зрения SEO) → выявленные проблемы → блок «Рекомендация:» жирным.
- Где нужно — код (robots.txt, sitemap.xml, llms.txt), таблицы, списки URL.

## Шаг 0. Единый сбор данных (общий коллектор)

Перед анализом запусти общий краулер-коллектор — он собирает список URL из sitemap, содержимое robots.txt и данные страниц, которые нужны для проверки индексации:

```bash
python3 .opencode/tools/seo_collect/site_collect.py --url <URL сайта>
```

Скрипт печатает путь к JSON (строка `OUT=...`, по умолчанию `/tmp/opencode/seo_collect/<хост>.json`) и кэширует его на 2 часа. Служебные файлы дополнительно проверяй напрямую (`/robots.txt`, `/sitemap.xml`, `/sitemap_index.xml`, `/sitemap/`, `/llms.txt`). Дальше данные бери из JSON/файлов скриптом на Python — сайт повторно вручную НЕ обходи.

Что в JSON:
- `pages[]` — по каждой странице: `status`, `final_url`, `redirect_chain`, `title`, `description`, `meta_robots`, `canonical`, `lang`, `headings`, `text`, `og`, `jsonld_types`, `structured_types`, `links_internal`, `images`, `soft404`;
- `internal_link_status` — отклик каждой внутренней ссылки (для проверки URL из sitemap);
- `sitemap` (`found`, `urls`, `files`), `robots` (`status`, `text`), `external_links`, `stats`.

Ключи: `--refresh` — пересобрать кэш; `--limit N` — ограничить число страниц; `--no-link-check` — без проверки откликов ссылок (быстрее).

## Порядок работы по пункту 1.4 «Индексация сайта»

> **Отчёты о ходе (для прогресс-бара).** При запуске из плагина выведи `[[stage:1/3]]` в начале, `[[stage:2/3]]` перед анализом и `[[stage:3/3]]` перед формированием `.docx`.

Пункт состоит из трёх подпунктов: **1.4.1 Robots.txt**, **1.4.2 Sitemap**, **1.4.3 llms.txt**.

1. Загружаем три служебных файла сайта:
   - `https://<host>/robots.txt`
   - `https://<host>/sitemap.xml` (и проверить варианты `/sitemap_index.xml`, `/sitemap/`)
   - `https://<host>/llms.txt`
   Проверять наличие/отсутствие (код отклика), содержимое, а также варианты `http`/`https` и `www`/без-www.
2. Для каждого файла пишем **краткую подводку** — зачем он нужен с точки зрения SEO.
3. Выявляем **ошибки и проблемы**:
   - **Синтаксис** (структура, корректные теги, допустимые значения).
   - **Дубли** (повторяющиеся записи/директивы; файл sitemap, упомянутый несколько раз и т.п.).
   - **Полнота** (все ли нужные страницы включены; нет ли лишних).
   - **Соответствие хосту** (единый canonical: `https://` + выбранный домен с www или без).
   - **Коды отклика** URL в sitemap (должны быть только 200).
4. Обязательно учитывать **CMS сайта** — какие технические разделы нужно закрыть/открыть (для robots.txt). Определить CMS (Bitrix, WordPress, самописная и т.д.) по характерным путям (`/bitrix/`, `/wp-admin/`, `/local/`, `?page=` и т.п.).
5. Формируем **рекомендации** по аналогии с образцом аудита Frontside.ru:
   - robots.txt — привести к готовому виду (код целиком);
   - sitemap.xml — перегенерировать, указать priority/changefreq по разделам (таблицей);
   - llms.txt — создать/переформировать (структура и правила).

### Эталон (по образцу Frontside.ru)
- **Robots.txt.** Отметить корректные директивы и неточности: избыточные директивы, блокировка динамики, отсутствие правил для ИИ-ботов, дублирование упоминания sitemap, незакрытые технические разделы (поиск и т.п.). В конце — приведённый к нужному виду файл целиком.
- **Sitemap.** Проверить синтаксис; перечислить ссылки с откликом 301/404 (в карте должны быть только 200); найти дублирование ссылок в разных блоках; проверить наличие `changefreq` и `priority`; рекомендовать значения `priority`/`changefreq` по разделам.
- **llms.txt.** Проверить язык (для русскоязычного сайта — русский), корректность символов (типа `faГ§ade`), отсутствие битых ссылок; дать рекомендацию по структуре файла.

### Что НЕ относится к пункту 1.4
- Адресация и ЧПУ — пункт 1.1.
- Дубликаты страниц — пункт 1.2.
- Отклики сервера в перелинковке — пункт 1.3.

## Техника

Использовать `requests` (при необходимости `pip3 install --break-system-packages requests`).
- Проверять отклик без/со следованием редиректам, чтобы отличить 200 от 301.
- Sitemap парсить как XML (для выявления ошибок синтаксиса), извлекать `<loc>`, `<lastmod>`, `<changefreq>`, `<priority>`.
- Сравнивать URL из sitemap с реальными страницами сайта (краулинг) для оценки полноты.

## Техника генерации .docx

Использовать `python-docx` (`pip3 install --break-system-packages python-docx`).
- `doc.styles['Normal'].font.size = Pt(10)`
- Обложка: заголовок Pt(24) 0x333333; дата Pt(9) 0x942972; таблица проекта (3 строки: шапка, «Заказчик», «Документ»), стиль `Table Grid`; «Содержание» Pt(20) 0x333333. Без «Текарта».
- Раздел: `add_heading('1.4. Индексация сайта', level=2)`; подпункты — `level=3` (`1.4.1. Robots.txt`, `1.4.2. Sitemap`, `1.4.3. llms.txt`).
- Код (robots.txt, sitemap) — отдельным абзацем моноширинным шрифтом (`Courier New`), каждая строка с новой строки.
- «Рекомендация:» — `run.bold = True`; перечисления — `List Bullet`.

После генерации проверить документ через `python-docx` и вывести краткую сводку по каждому из трёх файлов.

## Если проблем нет

Даже если по пункту проблем не выявлено — всё равно дай краткую подводку (зачем этот пункт нужен), а в блоке проблем напиши: «Проблем на сайте не обнаружено, исправления не требуются.»

## ОБЯЗАТЕЛЬНЫЕ ПРАВКИ ДМИТРИЯ (обязательно)
Robots.txt:
- Директива `Disallow: /*?` ДОЛЖНА быть в robots.txt — если её нет, это ошибка; если есть — ок.
- Не писать правила для ИИ-ботов (GPTBot, Google-Extended и т.п.).
- Не утверждать, что список закрытых адресов устарел: перепроверять страницы, при сомнении — проверять.
- Если пишем «не рекомендуется» — указывать причину.
Sitemap:
- Не рекомендовать `rel=next/prev` (устарело).
- Не пояснять очевидное (что changefreq/priority игнорируются Google).
- Не описывать не-проблемы.
