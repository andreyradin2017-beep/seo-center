# Технический аудит сайта (методология «Текарт»)

Проводим технический SEO аудит сайта и оформляем результаты в `.docx` по заданному шаблону.

## Формат итогового документа

На выходе всегда `.docx` файл, оформленный по шаблону как в примере («Технический аудит Frontside.ru.docx»):
- Обложка: название аудита (24pt, #333333), дата (9pt, #942972), таблица данных проекта (Заказчик / Документ). Без брендинга «Текарт» — без копирайта, дисклеймера и контактов менеджера.
- «Содержание» — список разделов
- Основные разделы (Heading 1), подразделы (Heading 2), вложенные (Heading 3)
- Каждый подраздел: констатация фактов → недостатки с примерами и ссылками → блок «Рекомендация:» жирным
- Где нужно — код, таблицы, гиперссылки, изображения

## Язык и стиль

- Понятным русским языком, без воды.
- Рекомендации — четкие и по пунктам (формат «Проблема X. ... → Рекомендация: ...»).
- Нейтральный, экспертный деловой тон, как в образце.

## Шаг 0. Единый сбор данных (общий коллектор)

Перед анализом запусти общий краулер-коллектор — один обход собирает данные для всех модельных пунктов и кэширует результат:

```bash
python3 .opencode/tools/seo_collect/site_collect.py --url <URL сайта>
```

Скрипт печатает путь к JSON (строка `OUT=...`, по умолчанию `/tmp/opencode/seo_collect/<хост>.json`) и кэширует его на 2 часа. Дальше данные бери из JSON скриптом на Python — сайт повторно вручную НЕ обходи.

Что в JSON:
- `pages[]` — по каждой странице: `status`, `final_url`, `redirect_chain`, `title`, `description`, `meta_robots`, `canonical`, `lang`, `headings` (H1–H6), `h1`, `text`, `text_len`, `og`, `twitter`, `jsonld_types`, `jsonld_blocks`, `microdata_types`, `structured_types`, `links_internal` (абсолютные URL), `links_external`, `images`, `soft404`;
- `internal_link_status` — отклик каждой внутренней ссылки (`status`, `location`);
- `sitemap` (`found`, `urls`, `files`), `robots` (`status`, `text`), `external_links`, `stats`.

Ключи: `--refresh` — пересобрать кэш; `--limit N` — ограничить число страниц; `--no-link-check` — без проверки откликов ссылок (быстрее).

## Порядок работы по пункту 1.2 «Дубликаты страниц»

> **Отчёты о ходе (для прогресс-бара).** При запуске из плагина выведи `[[stage:1/3]]` в начале, `[[stage:2/3]]` перед проверкой дубликатов и `[[stage:3/3]]` перед формированием `.docx`.

**Задача:** найти все дубликаты страниц — страницы с одинаковым (или почти одинаковым) контентом, которые доступны по разным URL и обе/все возвращают код отклика **200**.

Действовать строго по шагам:

1. Заходим на сайт, указанный пользователем.
2. Формируем список URL:
   - через `sitemap.xml`, если файл есть и рабочий;
   - если файла нет/с ошибками/неполный — обходим сайт по меню и внутренней перелинковке (краулинг).
3. Загружаем каждую страницу, у которой отклик 200, и извлекаем **основной контент** (тело страницы), исключая шаблон: меню, футер, счётчики, сайдбары. Если возможно — используем контейнер основного контента (`#content`, `.content`, `main`, `article`), иначе — эвристику.
4. Сравниваем страницы между собой:
   - **точные дубликаты** — совпадает нормализованный текст (хэш после удаления пробелов/пунктуации);
   - **близкие дубликаты** — высокая схожесть (например, Jaccard по шинглам слов ≥ 0.8);
   - отдельно проверяем типовые технические причины дублей:
     - `index.htm`/`index.php`/`index.html` vs `/`;
     - пагинация: `/news/` vs `/news/page-1/` vs `/news/page-0/`;
     - параметры: `?page=X` vs `?page=X&` vs `?page=X&page=X` vs другой регистр (`?page=Metal`), URL-кодирование символов (`%6d...`);
     - завершающий слеш/двойные слеши;
     - `www`/без `www`, `http`/`https` (если оба отдают 200, а не редирект);
     - поддомены с копией контента.
   - **Важно:** учитываем только пары, где обе страницы отдают **200** (редиректы 301/302 — это пункт про заголовки откликов, 1.3, не сюда).
5. Строим таблицу с двумя столбцами: **«Исходная страница»** и **«Дубликат»**. В «Исходную» ставим каноничную (основную) страницу, в «Дубликат» — лишний адрес с тем же контентом.
6. Оформляем раздел строго в структуре:
   - **подводка** — чем дубликаты плохи для SEO (размывание релевантности и позиций, непонимание поисковиком основной страницы, размытие ссылочного веса и краулингового бюджета, дубли в индексе, искажение аналитики);
   - **найденные проблемы** + таблица с проблемными страницами;
   - **рекомендации** по исправлению.

### Что НЕ относится к пункту 1.2 (исключить)
- Редиректы 301/302 и битые ссылки (404, 5xx) — это пункты про заголовки откликов сервера (1.3) и серверные факторы (4.x).
- Проблемы `sitemap.xml` — пункт про индексацию (1.4).
- Отсутствие ЧПУ как таковое — пункт 1.1 «Адреса страниц»; в 1.2 его упоминаем только как причину дублей.

### Шаблон подводки (можно адаптировать)
«Дубликаты страниц — это страницы с одинаковым или почти одинаковым контентом, доступные по разным URL. Дублирование негативно сказывается на SEO-продвижении: поисковым системам сложно определить, какую страницу считать основной и какую ранжировать; из-за «склеивания» страниц снижаются их позиции; размывается ссылочный вес и расходуется краулинговый бюджет; дубли могут попасть в индекс и конкурировать с основными страницами; искажается статистика. Дубликаты обычно возникают из-за технических особенностей адресации — параметров, регистра, слешей, кодировки, index-файлов и пагинации.»

### Рекомендации (типовые)
- Оставить один «канонический» адрес для каждого контента, остальные — закрыть 301-редиректом на канонический (или удалить, приведя к 404/410, если страница не нужна).
- Настроить `rel="canonical"` на всех страницах, указывающий на основной адрес.
- Для параметров: запретить лишние/мусорные параметры, привести регистр к единому, не допускать дублирования параметра; в идеале — внедрить ЧПУ.
- Для пагинации: первая страница — один адрес, `page-1`/`page-0` редиректить на него.
- Для `index.htm` и аналогов — 301 на `/`.
- Убедиться, что технические адреса-дубли не попадают в `sitemap.xml`.
- После исправления отправить затронутые страницы на переобход (Яндекс.Вебмастер, Google Search Console).

## Техника генерации .docx

Использовать Python библиотеку `python-docx` (установка при необходимости: `pip3 install --break-system-packages python-docx`).

Рекомендуемая структура скрипта (`/tmp/opencode/generate_audit.py`):
- `from docx import Document`, `from docx.shared import Pt, RGBColor`
- `doc.styles['Normal'].font.size = Pt(10)`
- Обложка: заголовок Pt(24) 0x333333; дата Pt(9) 0x942972; таблица данных проекта (3 строки: шапка, «Заказчик», «Документ»), стиль `Table Grid`. Копирайт/дисклеймер/контакты «Текарт» не добавлять.
- Таблица данных проекта: `doc.add_table(...)`, стиль `Table Grid`
- Заголовки: `doc.add_heading('...', level=1/2/3)`
- Таблица дубликатов: заголовок «Таблица N. Дубликаты страниц», шапка **«Исходная страница»** | **«Дубликат»**, каждая пара — строка.
- Жирная «Рекомендация: » — `run.bold = True`; маркированные списки — стиль `List Bullet`.

После генерации проверить содержимое через `python-docx` и вывести краткую сводку найденных дубликатов и структуру раздела.
