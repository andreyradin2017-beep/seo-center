# Правила проекта (opencode)

## SEO-центр (http://192.168.0.121:4180/)

При обработке задач из SEO-центра (плагин `.opencode/plugin/seo-ui.ts`, навыки
`seo-metatags-extract`, `seo-metatags`, `seo-topics`, `seo-articles`, `adresa-stranits`,
`dublikaty-stranits`, `zagolovki-otklikov-servera`, `wordstat`, `smm-groups`,
`mikrorazmetka`):

- **Сессии.** Каждая задача выполняется в отдельной сессии opencode. Задачи одного
  проекта (проект определяется по URL/хосту) группируются в одной сессии; разные URL —
  разные сессии. Плагин создаёт сессию с заголовком `SEO · <хост>` и переиспользует её
  для задач того же хоста.
- **Вкладки браузера.** Всегда открывай **новую** вкладку/страницу (новый `page`).
  НЕ используй и НЕ перезаписывай уже открытые вкладки пользователя.
- **Файлы результатов.** Сохраняй итоговые файлы только в папку задачи (`outDir`),
  переданную в промпте. Не создавай файлы в других местах.
- **Имена файлов.** Называй итоговый файл по имени задания (пункта), без названия сайта
  и без слов «Технический аудит». Примеры: `Адреса страниц.docx`, `Дубликаты страниц.docx`,
  `Заголовки откликов сервера.docx`. Хост и дату/время в имя файла не добавляй — папка
  запуска уже содержит хост и дату.
- **Прогресс.** Для длинных задач отмечай этапы маркерами `[[stage:N/M]]`.

## Правила SEO-аудитов (правки Дмитрия, docx `SEO-audit_pravki`)

Обязательно применять в КАЖДОМ техническом аудите. Источник — 46 комментариев
Дмитрия к аудиту pokras.ru.

Полная версия правил и схема `audit.json` (по ней панель считает скор, историю и
дельту) — в `.opencode/rules/audit-rules.md`. Промпты аудита ссылаются на этот
файл; при правках ниже синхронизируй оба места.

**Отчёт в целом**
- Указывать, **сколько страниц проверено**.
- «Положительное» — **отдельным блоком**, до списка недостатков.
- Если рекомендуешь что-то — давать **ровно 1 буквальный пример** «как должно быть».
- **Не описывать то, что не является проблемой**; не лить воду и очевидности.
- Не писать «регулярно перепроверять…».
- Где можно — оформлять **исправленный файл** (отдельный docx/txt) и ссылаться на него: «внедрите».
- Если сомневаешься — **проверь сам и дай правку**, либо не пиши вообще.
- **Не обрывать фразы/заголовки посреди слова**; писать нормально, без фанатизма с длиной.
- Ссылки писать **полными URL**.
- Термины: «**недоступны**» (не «недостижимы»); «**lazy load**» (не «ленивая загрузка»).
- Не писать про **аналитику/счётчики**, «ссылочные облака», `target="_blank"` без `noopener`.
- Не использовать термин «dofollow» — работаем в рамках `noindex`/`nofollow`.
- Не писать про `rel="sponsored"`.

**Meta / H1 / контент**
- **Title — 50–100 символов. Description — 170–250 символов.** Учитывать при генерации.
- Не обрезать title/description посреди слова ради лимита.
- Примеры в таблицах проверять, чтобы не было обрывков; исправленный вариант — корректный, без обрезки.
- Про метатеги писать «скорректировать, см. пункт N» и ссылаться на пункт выше.
- Совпадение текста писать приблизительно (например, «на 90%»).
- Если семядро приложено — писать «метатеги составлены с учётом запросов из сем. ядра»; фразу про «не приложено» не писать.
- Инфо-страницы (напр. `/useful/encyclopedia/`) тоже учитывать, чтобы был понятен расчёт среднего объёма.
- **Не писать слово «хост»** — сразу название файла таблицы и вкладку.

**Canonical**
- **Никогда** не писать «поставить `rel=canonical` на все страницы сам на себя».
- Разбирать canonical только на примерах (пагинация, каталог с цветами).
- Нет полезного вывода — не писать.

**Robots.txt**
- Не утверждать, что список закрытых адресов устарел — **перепроверять страницы**.
- Не писать про правила для ИИ-ботов (GPTBot и т.п.).
- Директива `Disallow: /*?` (закрытие параметров) **должна быть во всех robots**: нет — ошибка, есть — ок.
- Если пишем «не рекомендуется» — указывать **причину**.

**Sitemap**
- Не рекомендовать `rel=next/prev` (устарело).
- Не пояснять очевидное (changefreq/priority).

**Микроразметка / OpenGraph**
- Не проверять и не рекомендовать устаревшее: `WebSite`/`SearchAction`, `ItemList`/`CollectionPage`.
- Twitter-теги игнорировать; OpenGraph — общая.
- Использовать **только типы из справочника** `Микроразметка_Schema_org_справочник.xlsx` (в корне SEO-центра).
  - **JSON-LD** — для типов, которые Яндекс поддерживает в JSON-LD: `Article`, `NewsArticle`, `BlogPosting`, `Movie`, `Review`, `Recipe`, `QAPage`.
  - **Microdata** — для всех остальных типов (поддерживают и Яндекс, и Google).
  - Разметка/контент: **Organization / LocalBusiness / Store / MedicalOrganization** и т.п. — на «Контакты»/«О компании»; **BreadcrumbList** — на всех страницах кроме главной (текущий элемент не ссылка); **Product/Offer**, **Service**, **FAQPage (QAPage)**, **VideoObject**, **HowTo**, **Article/NewsArticle/BlogPosting/TechArticle** — по назначению страницы.
  - Даты — ISO 8601 (`2025-03-15` / `2025-03-15T10:30:00+03:00`); длительность — ISO 8601 (`PT1H30M`).
  - Для контента Яндекс требует `@id`, `headline`, `text (articleBody)`, минимум 500 символов.
  - Валидаторы: https://validator.schema.org/, Google Rich Results Test, Яндекс.Вебмастер (Микроразметка).

**Перебои в работе**
- Проверять через **https://ping-admin.ru/free_test/** и формировать корректную ссылку; не писать лишнее о том, кто что вернул.

**Сниппеты**
- Если не удаётся обойти капчу и сделать нормальные скриншоты — **пункт не делать** и написать, что не вышло; либо сделать корректные скриншоты (не «половина на англ. / половина чужих URL»).

## Админ-панель SEO-центра (`/admin`)

Реализована в `.opencode/plugin/seo-ui.ts`. Доступна ролям `admin` и `it` (ссылка
«Админ-панель» в шапке). Хранилище — `~/.config/opencode/seo-center-admin.json`
(chmod 600): пользователи, настройки, история запусков.

- **Роли.** `user` — сотрудник (видит только свои проекты); `admin` — видит все
  проекты, управляет пользователями/задачами/проектами; `it` — IT-администратор
  (логин `melnikov`), не отображается в списке пользователей, дополнительно видит
  вкладки «Логи» и «Бэкапы» (обычным админам они недоступны).
- **Вход.** Только именованные пользователи из админки. Общий доступ «любое имя +
  пароль promo» убран. Есть генератор пароля (8 символов). Legacy-пароль
  администратора (`ADMIN_PASSWORD`) оставлен как страховка владельца.
- **Безопасность входа.** Пароли пользователей хранятся scrypt-хешами; старые
  записи мигрируют при первом запуске новой версии. Встроенные пароли `promo`,
  `melnikov-admin` и фиксированный IT-пароль отозваны. Для IT-доступа задаётся
  `SEO_UI_IT_PASSWORD`; без секрета IT-вход выключен. Если в старом
  `seo-center-admin.json` нет именованных учётных записей, задайте пароль
  администратора через `SEO_UI_ADMIN_PASSWORD` перед запуском.
- **Разделы.** Обзор (сводка + лимит одновременных аудитов/ретеншен), Пользователи,
  Задачи и очередь (отмена, история), Проекты и файлы (раскрытие, скачивание,
  очистка), Логи и Бэкапы (только `it`). Вкладка «Модели» удалена.
- **API.** Все под `/api/admin/*`, только для `admin`/`it`; `logs`, `backups`,
  `backup`, `download-archive` — только для `it`.
- **Обычные вкладки.** Админ и IT видят все проекты; сотрудник — только свои.

## Тест/прод-контур и развязка панели (реализовано)

- **Тест-инстанс:** `opencode-seo-test.service` — агент `opencode serve :4199`,
  панель на `:4181` (бейдж «ТЕСТ»), свои данные: `SEO_RESULTS_DIR=seo-results-test`,
  `SEO_QUEUE_STATE_FILE=seo-results-test/.queue.json`. Включается: `./deploy.sh test`.
- **Развязка панели и агента.** Панель можно поднимать отдельным процессом
  (`.` вне `.opencode`): `SEO-центр/seo-panel/panel.ts` — подключается к агенту по
  HTTP/SSE через `@opencode-ai/sdk` (`createOpencodeClient`, `client.global.event()`),
  запускается `node --experimental-strip-types`. Агент при этом не обслуживает панель
  (`SEO_PANEL_EXTERNAL=1` в юните агента). Итог: рестарт панели не трогает агента и
  запущенные аудиты; панель переживает рестарт агента (SSE переподключается).
  Юнит: `opencode-seo-panel-test.service` (`:4181` → агент `:4199`).
- **Важно:** opencode вызывает ВСЕ экспортированные функции модуля плагина как
  плагины → `createSeoPanel` защищён проверкой `opts.projectDir` (настоящий вызов).
- **Кнопка рестарта** в админке перезапускает юнит из `SEO_UNIT_NAME` (у панели —
  свой юнит), поэтому на тесте она рестартит панель, а не агента.
- **deploy.sh:** `check` (синтаксис + security-тесты), `deploy`
  (архив исходников→рестарт прод→health→авто-откат на последнюю рабочую версию),
  `rollback`, `test`, `test-stop`, `list`.
- **Прод (развязка, ещё не включена):** аналогично нужен
  `opencode-seo-panel.service` (`:4180` → агент `:4098`) и `SEO_PANEL_EXTERNAL=1`
  в `opencode-seo.service`. Включается из терминала пользователя (рестарт прод-агента
  обрывает текущий процесс агента/сессии).

## Тест/прод-деплой (идеи, отложено — вернуться по запросу)

Задача: править код, тестировать на тесте, затем заливать на прод всем коллегам.
Применение изменений = рестарт сервиса (плагин читается при старте).

- **Принципы:** код в git, данные/секреты вне git; правки только в `dev`, прод —
  `main`; деплой атомарный (бэкап → merge/checkout → рестарт → health-check →
  авто-откат при провале).
- **Вариант A (рекомендован):** git-ветки `main`/`dev`; тестовый инстанс на порту
  4181 из отдельного worktree (`git worktree add ../seo-test dev`), свой
  `SEO_UI_PORT`, свой каталог результатов, бейдж «ТЕСТ»; второй юнит
  `opencode-seo-test.service`. Промоут — merge `dev → main` + рестарт прод.
- **Вариант B (проще):** тестировать локально в `dev`, затем `deploy.sh` копирует
  проверенные файлы в прод и рестартит.
- **Вариант C (на будущее, несколько машин):** Docker — прод/тест в контейнерах,
  разные порты/томы.
- **Обязательно:** `deploy.sh` с авто-откатом и health-check (`/api/health`);
  версионирование/теги и `deploy.sh rollback`; секреты и данные вне git
  (`seo-center-auth.json`, `seo-center-admin.json`, `.omniroute/`, `seo-backup-pass`);
  миграции формата admin-файла/индекса; тестовый инстанс не пишет в боевой
  `seo-results/` (вынести корень результатов в env, напр. `SEO_RESULTS_DIR`);
  бэкап перед деплоем (навык `seo-center-backup`).
- **В админку позже:** блок «версия/окружение/ветка/последний деплой», кнопки
  «Задеплоить dev → prod» и «Откатить», история деплоев.
- **Рекомендация:** начать с Варианта A в минимуме (ветки, тестовый юнит на 4181,
  `deploy.sh` с авто-откатом), контейнеры/кнопки — позже.
